# Upgrade Channel Delivery to 2.1.0

This guide covers upgrades from 2.0.0 to [published v2.1.0](https://github.com/Maatify/channel-delivery/releases/tag/v2.1.0).
For 1.x or pre-keyed installations, follow the
[2.0.0 migration path](2.0.0.md) first. The new worker uses the committed
`maatify/email-delivery` 1.3.0 lock and requires PHP 8.4 or later with PDO MySQL.
Keep the service's PHPMailer 6.x line and install with `composer install --no-dev`.

## Check the queue schema

A normal installation already has `idx_worker_poll_priority (status, priority, id)`
from service migration `003_optimize_worker_poll_index.sql`. Keep that index, the
existing retry indexes and `updated_at TIMESTAMP ... ON UPDATE CURRENT_TIMESTAMP`.
The lease reuses this column and compares instants across database session time zones.
The upgrade leaves historical rows, ciphertext, keys, receipt bindings and the clocks
used for legacy and receipt-bound due/retry/sent times in place.

Inspect indexes and column types before switching workers.

```sql
SHOW COLUMNS FROM cd_email_queue LIKE 'updated_at';
SHOW INDEX FROM cd_email_queue;
```

| Installation | Action |
| --- | --- |
| Existing supported service schema | Keep service 001–003 and all migrations already applied. The worker upgrade needs no new SQL on this schema. |
| Fresh service or enabling an optional endpoint | Follow the [endpoint schema matrix](../guides/USAGE_GUIDE.md#choose-the-schema). Either v2 operation needs service 004 and a consumer binding. Apply package 002/003 for real v2 receipts and package 004 for synthetic recording. |
| Custom schema without a usable index starting with `(status, priority, id)` | Review the schema against the supported baseline. For an otherwise compatible custom queue, apply the installed package's `schema/mysql/005_email_queue_claim_index.sql` once, during an off-peak window. Its online DDL still takes metadata locks. |

Use the service's queue definition for fresh installs. Reserve the vendor's index
006 for applications that run entity-type scoped batches. This service runs unscoped
batches. Boot, worker, status and HTTP commands leave migrations to the operator.

## Review prior attempts before starting workers

The old scheduled reset could leave a `pending` job with four or more attempts.
Every new worker connection checks for those rows before it reaches the engine.
The worker exits with code `3` and the read-only queue status reports
`exhausted_pending` while any such row remains. Scheduled and retry-delayed rows
are included. Run this preflight with all previous workers and the old reset
stopped, with the new workers still stopped.

```sql
SELECT id, attempts, status, scheduled_at, retry_after, updated_at
FROM cd_email_queue
WHERE status = 'pending' AND attempts >= 4
ORDER BY id;
```

Review the returned jobs and preserve the operator's audit record before changing
their statuses. SMTP delivery may already have occurred. If the operator approves
terminal settlement, mark only the reviewed IDs as failed and leave the attempt
counts, ciphertext and receipt bindings in place. In the following example,
replace the example IDs with those approved for settlement.

```sql
UPDATE cd_email_queue
SET status = 'failed', last_error = 'legacy_attempt_limit_reached'
WHERE id IN (101, 102) AND status = 'pending' AND attempts >= 4;
```

Repeat the read-only check until no rows remain. Keep the old reset disabled.
This procedure concerns exhausted `pending` rows. The engine settles expired
`processing` rows at the cap as `processing_lease_expired`.

## Switch workers

1. Record the current artifact and configuration, back up the database and verify the
   restore procedure. Retain the decryption keys needed by queued jobs and receipts.
2. Pause the old queue worker schedules and wait for active batches to finish. Disable
   any legacy scheduled stuck-job reset so lease recovery has one owner. Keep API
   ingestion available if the HTTP release switch can be done independently.
3. Complete the [prior-attempt preflight](#review-prior-attempts-before-starting-workers)
   and review remaining `processing` jobs before starting the new worker. The first
   batch can reclaim expired jobs under the attempt cap, including a job whose SMTP
   send succeeded before its status was committed. Review expired time-sensitive jobs
   and ambiguous deliveries according to the owning application's policy. Leave
   control over those decisions with the operator.
4. Install the reviewed project artifact and committed dependencies. Set
   `DB_SESSION_WAIT_TIMEOUT` if the default of 28,800 seconds is unsuitable, and
   `EMAIL_PROCESSING_LEASE_SECONDS` if the longest expected batch plus a margin
   can approach 300 seconds. Reduce `--batch` to shorten waiting within a claim.
   Keep the original database time zone for legacy scheduling semantics.
   [Lease sizing](../how-to/run-worker.md#processing-lease)
   Verify the existing `MAIL_ENCRYPTION` setting. Use `tls` or `ssl` as the
   provider requires, or empty/unset when an unencrypted relay is intentional.
   An unsupported value now prevents transport initialization.
   With the affected processes stopped, run `php scripts/deploy_clear_cache.php`
   before restarting them on the updated artifact. Preserve existing template
   configuration. Verify that the runtime accounts can create and write the compiled
   Twig and DI cache directories after cleanup. [Cache procedure](../reference/configuration.md#compiled-caches)
5. Start the new workers together. Give each a separate writable heartbeat file
   outside `public/`, then configure queue-status alerts with a heartbeat allowance
   above the longest expected batch plus idle sleep. Include every worker state
   file in the monitor to receive outcome-write and attempt-cap alerts. The [worker guide](../how-to/run-worker.md)
   covers systemd, Supervisor, exit codes and log events.
6. On an isolated staging queue verify v1 acceptance, v2 acceptance and receipt replay
   where enabled, and synthetic isolation where enabled. Observe a controlled worker
   connection loss and verify recovery, a successful next batch, and the queue-status
   alert/recovery cycle for both connection and outcome-write failures. Verify actual SMTP and mailbox delivery separately with a
   designated staging recipient.

## Roll back

Pause the new workers and verify all active batches have stopped. Restore the
2.0.0 artifact, committed vendor lock and worker/monitor configuration
into a clean release directory with empty compiled caches. Channel Delivery
2.0.0 predates the cache-clear CLI. Keep the existing schema and queue rows.
A compatible claim index added for a custom schema can remain. A database
restore requires reconciling new acceptances since the backup.

The older worker has no processing-lease recovery. Keep every schedule for
`scripts/recover_stuck_jobs.php` disabled throughout the rollback. Use the settlement below with all
email workers and reset jobs for this queue paused, including one-shot jobs and
process-manager restarts. Let active batches drain when possible and verify no
worker is still running before making changes. API enqueues can continue
independently if they only insert new jobs.

### Processing settlement during rollback

1. Before starting the older worker, inventory **all** `processing` rows. For the
   service's `TIMESTAMP` column, use a UTC operator session consistently for
   the inventory, review and settlement. Record the job ID, attempts, update
   timestamp, previous error and the evidence behind each decision in the
   restricted operations record. If the receipt-binding migration is provisioned,
   check whether `enqueue_receipt_id` is set for each job.

   ```sql
   SET SESSION time_zone = '+00:00';
   SELECT id, attempts, scheduled_at, retry_after, updated_at, sent_at, last_error
   FROM cd_email_queue
   WHERE status = 'processing'
   ORDER BY updated_at, id;
   ```

2. Review the worker and relay evidence for the exact job. Choose one action per
   row with the queue owner's approval.

   | Evidence and policy | Action |
   | --- | --- |
   | The relay accepted the message and the acceptance timestamp is verified. | Record `sent` with the verified acceptance time, even if the attempt cap was reached. |
   | There is positive evidence that the message was never handed off, `attempts < 4`, and the owner approves a retry that is still valid. | Return the job to `pending`, preserving its attempt count and scheduling. |
   | The outcome is unknown, the attempt cap is reached without verified acceptance, or a retry is no longer appropriate. | Park the job as terminal `failed` with `rollback_delivery_unknown`, `rollback_attempt_limit_reached` or `rollback_retry_not_approved` as appropriate. This is an operational disposition. A failed or missing database write and missing logs alone do not establish that delivery did not occur. |

3. Lock and update only the reviewed row in one transaction. Bind the placeholders
   below to the reviewed values in the same UTC operator session, or substitute
   exact SQL literals when using an interactive client. The lock query must return
   exactly that row. Run **one** update for the approved disposition. For `sent`,
   bind the verified relay acceptance time expressed in UTC for a receipt-bound
   row or in the legacy worker's database session time zone for an unbound row.
   `sent_at` is a `DATETIME`. The UTC operator session controls the `updated_at`
   comparison and does not convert that supplied wall-clock value.

   ```sql
   START TRANSACTION;
   SELECT id, attempts, updated_at
   FROM cd_email_queue
   WHERE id = :job_id AND status = 'processing'
     AND attempts = :reviewed_attempts AND updated_at = :reviewed_updated_at
   FOR UPDATE;

   -- Run only one of these three updates.
   UPDATE cd_email_queue
   SET status = 'sent', sent_at = :verified_sent_at
   WHERE id = :job_id AND status = 'processing'
     AND attempts = :reviewed_attempts AND updated_at = :reviewed_updated_at;

   UPDATE cd_email_queue
   SET status = 'pending', last_error = 'rollback_confirmed_unsent'
   WHERE id = :job_id AND status = 'processing' AND attempts < 4
     AND attempts = :reviewed_attempts AND updated_at = :reviewed_updated_at;

   UPDATE cd_email_queue
   SET status = 'failed', last_error = :settlement_reason
   WHERE id = :job_id AND status = 'processing'
     AND attempts = :reviewed_attempts AND updated_at = :reviewed_updated_at;

   SELECT ROW_COUNT() AS changed_rows;
   ```

   Run `COMMIT` only if one row changed. Otherwise `ROLLBACK`, re-read the row
   and review the conflict. The procedure preserves the row, attempts, encrypted
   data, receipt binding, schedule and retry time. Leave rows settled as `sent`
   or `failed` terminal.
   Repeat the inventory and the [prior-attempt preflight](#review-prior-attempts-before-starting-workers).
   Start the older worker only once there are no `processing` rows left from the
   stop and no exhausted `pending` rows, including delayed ones.

4. While running the older worker, assign an operator to monitor `processing`
   ages at a defined cadence and investigate every unexpected worker exit or
   restart. Use the read-only inventory above and alert when a row's age exceeds
   the longest expected claimed batch plus a safety margin. This check is
   required alongside ordinary pending-queue monitoring. When a job is stuck,
   pause and drain all email workers again and repeat the same inventory,
   settlement and preflight before resuming.

With the lease-enabled worker, a send with an unrecorded outcome can be
retried when attempts remain. At the four-attempt cap, the lease-enabled worker
records `failed` with `processing_lease_expired` without another send. Treat
`sent` as an SMTP transport outcome and confirm mailbox receipt through the
destination when that distinction matters.
