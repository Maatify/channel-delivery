# Upgrade Channel Delivery to 2.1.0

This guide covers upgrades from 2.0.0. For 1.x or pre-keyed installations, follow the
[2.0.0 migration path](2.0.0.md) first. The new worker uses the committed
`maatify/email-delivery` 1.3.0 lock and requires PHP 8.4 or later with PDO MySQL.
Keep the service's PHPMailer 6.x line and install with `composer install --no-dev`.

## Check the queue schema

A normal installation already has `idx_worker_poll_priority (status, priority, id)`
from service migration `003_optimize_worker_poll_index.sql`. Keep that index, the
existing retry indexes and `updated_at TIMESTAMP ... ON UPDATE CURRENT_TIMESTAMP`.
The lease reuses this column and compares instants across database session time zones.
The upgrade leaves historical rows, ciphertext, keys, receipt bindings and the clocks
used for legacy and receipt-bound due/retry/sent times in place.

Inspect indexes and column types before switching workers.

```sql
SHOW COLUMNS FROM cd_email_queue LIKE 'updated_at';
SHOW INDEX FROM cd_email_queue;
```

| Installation | Action |
| --- | --- |
| Existing supported service schema | No new SQL. Keep service 001–003 and any already applied v2 or synthetic migrations. |
| Fresh service | Apply service 001–003. Add service 004 and vendor 002/003 for real v2, then vendor 004 if synthetic recording is needed. Follow the [atomic rollout](../how-to/atomic-email-rollout.md) and [synthetic setup](../how-to/synthetic-email-operations.md). |
| Custom schema without a usable index starting with `(status, priority, id)` | Review the schema against the supported baseline. For an otherwise compatible custom queue, apply the installed package's `schema/mysql/005_email_queue_claim_index.sql` once, during an off-peak window. Its online DDL still takes metadata locks. |

Use the service's queue definition for fresh installs. Reserve the vendor's index
006 for applications that run entity-type scoped batches. This service runs unscoped
batches. Boot, worker, status and HTTP commands leave migrations to the operator.

## Review prior attempts before starting workers

The old scheduled reset could leave a `pending` job with four or more attempts.
Every new worker connection checks for those rows before it reaches the engine.
The worker exits with code `3` and the read-only queue status reports
`exhausted_pending` while any such row remains. Scheduled and retry-delayed rows
are included. Run this preflight with all previous workers and the old reset
stopped, with the new workers still stopped.

```sql
SELECT id, attempts, status, scheduled_at, retry_after, updated_at
FROM cd_email_queue
WHERE status = 'pending' AND attempts >= 4
ORDER BY id;
```

Review the returned jobs and preserve the operator's audit record before changing
their statuses. SMTP delivery may already have occurred. If the operator approves
terminal settlement, mark only the reviewed IDs as failed and leave the attempt
counts, ciphertext and receipt bindings in place. In the following example,
replace the example IDs with those approved for settlement.

```sql
UPDATE cd_email_queue
SET status = 'failed', last_error = 'legacy_attempt_limit_reached'
WHERE id IN (101, 102) AND status = 'pending' AND attempts >= 4;
```

Repeat the read-only check until no rows remain. Keep the old reset disabled.
This procedure concerns exhausted `pending` rows. The engine settles expired
`processing` rows at the cap as `processing_lease_expired`.

## Switch workers

1. Record the current artifact and configuration, back up the database and verify the
   restore procedure. Retain the decryption keys needed by queued jobs and receipts.
2. Pause the old queue worker schedules and wait for active batches to finish. Disable
   any legacy scheduled stuck-job reset so lease recovery has one owner. Keep API
   ingestion available if the HTTP release switch can be done independently.
3. Complete the [prior-attempt preflight](#review-prior-attempts-before-starting-workers)
   and review remaining `processing` jobs before starting the new worker. The first
   batch can reclaim expired jobs under the attempt cap, including a job whose SMTP
   send succeeded before its status was committed. Review expired time-sensitive jobs
   and ambiguous deliveries according to the owning application's policy. Leave
   control over those decisions with the operator.
4. Install the reviewed project artifact and committed dependencies. Set
   `DB_SESSION_WAIT_TIMEOUT` if the default of 28,800 seconds is unsuitable, and
   `EMAIL_PROCESSING_LEASE_SECONDS` if the longest expected batch plus a margin
   can approach 300 seconds. Reduce `--batch` to shorten waiting within a claim.
   Keep the original database time zone for legacy scheduling semantics.
   [Lease sizing](../how-to/run-worker.md#processing-lease)
   Verify the existing `MAIL_ENCRYPTION` setting. Use `tls` or `ssl` as the
   provider requires, or empty/unset when an unencrypted relay is intentional.
   An unsupported value now prevents transport initialization.
   With the affected processes stopped, run `php scripts/deploy_clear_cache.php`
   before restarting them on the updated artifact. Preserve existing template
   configuration. Verify that the runtime accounts can create and write the compiled
   Twig and DI cache directories after cleanup. [Cache procedure](../reference/configuration.md#compiled-caches)
5. Start the new workers together. Give each a separate writable heartbeat file
   outside `public/`, then configure queue-status alerts with a heartbeat allowance
   above the longest expected batch plus idle sleep. Include every worker state
   file in the monitor to receive outcome-write and attempt-cap alerts. The [worker guide](../how-to/run-worker.md)
   covers systemd, Supervisor, exit codes and log events.
6. On an isolated staging queue verify v1 acceptance, v2 acceptance and receipt replay
   where enabled, and synthetic isolation where enabled. Observe a controlled worker
   connection loss and verify recovery, a successful next batch, and the queue-status
   alert/recovery cycle for both connection and outcome-write failures. Verify actual SMTP and mailbox delivery separately with a
   designated staging recipient.

## Roll back

Stop and drain the new workers before restarting the old ones. Restore the previous
artifact, committed vendor lock and worker/monitor configuration into a clean
release directory with empty compiled caches. When reusing the previous release
directory, use its documented procedure to clear both compiled caches before
restarting processes. Channel Delivery 2.0.0 predates the cache-clear CLI. Use a
clean release directory for a rollback to that version. Repeat the prior-attempt
preflight before starting the older worker, keep the old reset disabled, and
review any remaining `processing` jobs. Keep settled rows terminal, with their
attempts and receipt bindings intact. Leave the existing schema and queue rows
in place. A compatible claim index added for a custom schema can remain, and a database restore requires
reconciling all new acceptances since the backup.

After a send with an unrecorded outcome, the lease permits redelivery when attempts
remain. At the four-attempt cap the worker records `failed` with
`processing_lease_expired` without another send. Delivery is at-least-once, so
treat `sent` as a recorded SMTP transport outcome and confirm mailbox receipt
through the destination when that distinction matters.
