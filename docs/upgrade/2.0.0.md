# Upgrade to project 2.0.0

Project2.0.0 was published on2026-11-07; see the
[release source and qualification record](../releases/2.0.0.md).
**Project2.0.0 does not remove HTTPv1.**

## Compatibility changes

- Raise runtime from PHP^8.2 to **PHP^8.4** and verify the PDO MySQL driver and all
  manifest extensions. PHP8.2/8.3 consumers cannot install this project release.
  This requirement is for hosting/installing the service, not for remote HTTP clients.
  The underlying email-delivery library retains its own broader PHP policy.
- Deploy the committed project Composer lock; the service uses email-delivery^1.2,
  currently locked to1.2.0. Do not choose migrations from an unrelated package checkout.
- HTTPv1 retains its per-call insert and `202 queued`; an Idempotency-Key there does
  not deduplicate. Existing valid callers and SMTP/retry policy stay as before.
- Atomic HTTPv2 and synthetic recording are additive, explicitly provisioned features.

The major version reflects the approved PHP compatibility break, not merely the new
endpoints or documentation. [Security support](../../SECURITY.md) is separate from
runtime compatibility and publication;1.x support is not withdrawn by this preparation.

## Existing installation

1. Back up data and retain old source/dependency lock/configuration for rollback.
2. Upgrade PHP/extensions and install the new reviewed source/lock. Do not publish
   the repository root; keep the web root at public/.
3. Keep existing service migrations001–003. For real v2, apply
   `migrations/004_create_email_consumer_bindings.sql`, then installed-package
   `schema/mysql/002_email_enqueue_receipts.sql` and `003_email_queue_receipt_binding.sql`
   **once**. See [preconditions/order](../how-to/atomic-email-rollout.md).
   Fresh service001 is the historical service queue, not the library's newer001.
4. Provision stable API-key consumer bindings explicitly; do not derive namespace
   from a raw key, key name or row id. Bind rotated keys to the same approved identity.
5. Only if enabling synthetic calls, apply installed-package
   `004_email_synthetic_requests.sql`, set explicit retention and arrange bounded
   cleanup/monitoring. No automatic cron or schema update runs on boot.
6. Correct sample names to MAIL_DEBUG_LEVEL, keep APP_DEBUG=false, and configure
   exact proxy IPs (CIDR is unsupported). Clear stale compiled DI/Twig caches using
   your deployment process; the Athar fork has its own existing cache-clear script.
7. Restart/reload long-running workers through your process manager on the new
   dependency set. Validate health and a dedicated controlled intent, then compare
   replay/lookup and worker processing separately from actual mailbox confirmation.

## Recovery guarantees and rollback

Persist real v2 intent/key before HTTP. Preserve the immutable body, namespace,
receipt retention and historical decrypt keys.503/timeout is uncertain; query and
retry the same identity. Never switch to v1 or generate a new key to hide uncertainty.
A missing queue row does not authorize recreation while its receipt survives.

Synthetic rows are inert, not receipts; retry can append another inert row.
Keep their maintenance available for the approved retention horizon and do not copy
them into the queue. A rollout rollback must preserve receipts, binding columns and
read keys required by already accepted v2 intents. Stop new optional callers first;
do not drop schema or delete data as a code rollback shortcut.

No production migration, rollout or account-flow change is authorized or proven by
release preparation. Consumer public-response normalization and durable host intent
remain separate integration work.
